SSH (Secure Shell) - сетевой протокол для безопасного удалённого подключения к другому компьютеру. SSH работает поверх [[TCP]]. Стандартный [[ports]] `22`.

Через SSH можно:
- удалённо войти на сервер;
- выполнять команды;
- копировать файлы;
- делать туннели;
- использовать Git по SSH;
- автоматизировать деплой.

## Как работает SSH

### Транспортный слой

**`Задача:`** Превратить обычное [[TCP]] соединение в шифрованное.
1. Клиент открывает [[TCP]] соединение на порт 22.
2. Обе стороны отправляют друг другу строку с названием и версией своей программы (открытым текстом).
3. Стороны обмениваются списками того, что каждая умеет:
	- Какими способами готова обмениваться ключами.
	-  Какими шифрами шифровать. 
	-  Чем проверять целостность.
	Из этих списков ерется первый вариант который есть у обоих. 
4. Обе машины выполняют обмен ключами и получают общий секрет.
	Наружу уходят только публичные половины, а сам секрет ни разу не покидает машины. Из него обе стороны нарезают рабочие ключи. 

У каждого сервера есть постоянная пара ключей - ее называют хостовым ключом. Создается она один раз при установке. В конце обмена ключами сервер подписывает своим закрытым хостовым ключом отпечаток всего разговора который только что состоялся. Клиент провреяет эту подпись и если она сходится - свежий сессионный ключ намертво связан с личностью сервера. 

В отличии от браузера, гда за подтверждение подлинности ключа отвечают удостоверяющие центры, в [[linux/ssh|ssh]] идут на честный компромисс который называется доверием при первой встрече. При первом подлючении нам предлагают сверить короткий [[хеш]] открытого ключа сервера. Как только мы отвечаем `yes` ключ записывается в `~/.ssh/known_hosts` на машине. И дальше при каждом новом подключении клиент молча сверяет предьявленный ключ с сохраненным. 

### Слой аутентификации 

Он работает уже внутри зашифрованного соединения.  В нормальных системах аутентификация работает по ключу, а доступ по паролю закрыт. На сервере в файле `~/.ssh/authorized_keys` лежит ваш открытый ключ, который туда кладется один раз. При входе клиент берет блок данных, подписывает его закрытым ключом и отправляет только подпись. Сервер проверяет подпись открытым ключом из файла и если она сходится значит на том конце действительно есть закрытый ключ. 

Первым в подписываемый блок кладется идентификатор сессии, полученный из обмена ключами и уникален для этого соединения. Из-за этого подпись годится только один раз, для одной сессии. Если вы зашли на чужой сервер его владелец не сможет взять вашу подпись и предьявить ее другому серверу о вашего имени. 

### Слой соединения

Прошлоый слой был просто шифрованной связью. Делает внутри этой связи несколько шифрованных каналов. У каждого есть свой номер и свой поток данных.

## SSH Transport Layer

**`Задача:`** превратить обычное TCP-соединение в защищённый канал.

1. Клиент открывает TCP-соединение с сервером на порт `22`.
2. Клиент и сервер отправляют друг другу строки с названием и версией своей SSH-реализации.
3. Стороны обмениваются списками поддерживаемых алгоритмов:
    - обмена ключами;
    - шифрования;
    - проверки целостности;
    - сжатия.
4. Из этих списков выбираются алгоритмы, которые поддерживают обе стороны.
5. Клиент и сервер выполняют обмен ключами и независимо получают одинаковый общий секрет.
6. На основе общего секрета создаются сессионные ключи, которыми шифруется текущее соединение.

Сам общий секрет по сети не передаётся.

Пример логики:

```text
Клиент                    Сервер
   │                         │
   ├──── параметры ─────────►│
   │◄─── параметры ──────────┤
   │                         │
   ├──── обмен ключами ─────►│
   │◄─── обмен ключами ──────┤
   │                         │
   ▼                         ▼
Одинаковый общий секрет
        ↓
Сессионные ключи
        ↓
Зашифрованное соединение
```

### Host Key

У SSH-сервера есть постоянная пара ключей — **host key**.

Она идентифицирует сам сервер.

```text
Private Host Key
→ хранится только на сервере

Public Host Key
→ показывается клиентам
```

Во время обмена ключами вычисляется специальный хеш текущего соединения.

Сервер подписывает этот хеш своим закрытым host key.

Клиент проверяет подпись по открытому host key сервера.

Таким образом сессионный ключ связывается с конкретным сервером.

Важно различать:

```text
Session Key
→ шифрует конкретное SSH-соединение

Host Key
→ подтверждает личность сервера
```

## Проверка сервера

В отличие от HTTPS, где доверие к серверу обычно подтверждают удостоверяющие центры, SSH часто использует модель:

```text
TOFU
Trust On First Use
Доверие при первом использовании
```

При первом подключении SSH показывает fingerprint host key сервера.

Пример:

```text
SHA256:xxxxxxxxxxxxxxxxxxxxxxxx
```

Если пользователь подтверждает подключение, публичный host key сервера сохраняется в:

```bash
~/.ssh/known_hosts
```

При следующих подключениях SSH сравнивает ключ сервера с сохранённым.

Если ключ внезапно изменился, SSH может показать:

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

Причины могут быть разные:

- сервер переустановили;
    
- SSH host key поменялся;
    
- IP теперь принадлежит другому серверу;
    
- возможна MITM-атака.
    

Fingerprint — это короткий хеш публичного host key, удобный для ручной проверки.

## SSH Authentication Layer

После создания зашифрованного соединения начинается аутентификация пользователя.

Она происходит уже внутри защищённого канала.

SSH поддерживает разные способы аутентификации:

- пароль;
    
- SSH-ключ;
    
- другие методы.
    

Для серверов обычно предпочтительна аутентификация по SSH-ключам.

### Аутентификация по ключу

У пользователя есть пара ключей:

```text
Private Key
Public Key
```

Приватный ключ хранится только у клиента.

Публичный ключ пользователя хранится на сервере в:

```bash
~/.ssh/authorized_keys
```

При подключении клиент не отправляет приватный ключ серверу.

Вместо этого:

```text
Клиент
   ↓
Подписывает данные своим Private Key
   ↓
Отправляет подпись серверу
   ↓
Сервер проверяет подпись Public Key
из authorized_keys
   ↓
Если подпись верна — пользователь подтверждён
```

Таким образом приватный ключ никогда не покидает клиентскую машину.

В подписываемые данные входит идентификатор текущей SSH-сессии.

Поэтому подпись связана с конкретным соединением и её нельзя просто перехватить и повторно использовать на другом сервере.

## SSH Connection Layer

После:

```text
TCP-соединения
↓
шифрования
↓
проверки сервера
↓
аутентификации пользователя
```

создаётся SSH Connection Layer.

Его задача — организовать внутри одного SSH-соединения несколько независимых каналов.

```text
SSH-соединение
│
├── Shell
├── Выполнение команды
├── SFTP
├── Local Port Forwarding
├── Remote Port Forwarding
└── другие каналы
```

У каждого канала есть собственный идентификатор и отдельный поток данных.

Это называется **мультиплексированием**.

Например, одно TCP-соединение:

```text
Client:54321 → Server:22
```

может переносить несколько разных SSH-каналов.

### Shell

Интерактивный терминал:

```bash
ssh user@server
```

### Выполнение команды

```bash
ssh user@server "uptime"
```

### SFTP

Передача файлов через SSH:

```bash
sftp user@server
```

### Port Forwarding

SSH может передавать TCP-соединения через зашифрованный канал.

Например:

```bash
ssh -L 8080:localhost:80 user@server
```

Схема:

```text
localhost:8080
      ↓
SSH-канал
      ↓
server:80
```

## Полная схема SSH

```text
Клиент
  │
  │ TCP :22
  ▼
Сервер
  │
  ▼
SSH Transport Layer
  │
  ├─ согласование алгоритмов
  ├─ обмен ключами
  ├─ получение общего секрета
  ├─ создание session keys
  └─ проверка host key сервера
  │
  ▼
Зашифрованный канал
  │
  ▼
SSH Authentication Layer
  │
  ├─ пароль
  └─ SSH-ключ
  │
  ▼
Пользователь подтверждён
  │
  ▼
SSH Connection Layer
  │
  ├─ Shell
  ├─ Exec
  ├─ SFTP
  ├─ Port Forwarding
  └─ другие каналы
```

## Что важно запомнить

- SSH работает поверх TCP.
    
- Стандартный порт — `22/TCP`.
    
- SSH сначала создаёт защищённое соединение, потом аутентифицирует пользователя.
    
- Session key используется для шифрования конкретного соединения.
    
- Host key используется для идентификации сервера.
    
- Host key сервера сохраняется в `~/.ssh/known_hosts`.
    
- Публичные ключи пользователей хранятся в `~/.ssh/authorized_keys`.
    
- Private key никогда не передаётся по сети.
    
- Внутри одного SSH-соединения может существовать несколько независимых каналов.
    
- SSH используется не только для терминала, но и для SFTP, туннелей, Git и автоматизации.
