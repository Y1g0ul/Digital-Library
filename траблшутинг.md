## Цель 1: Охарактеризовать сервер.

Выясните, чем занимается сервер; каково его назначение (например, веб-сервер, сервер баз данных, сервер обработки данных и т. д.).
``` bash
sudo netstat -tlpn  # becoming obsolete
sudo ss -tlpn  # more modern (same flags!)
```
Конечно, мы можем использовать этот метод [[ps]] и для перечисления всех процессов:
``` bash
sudo ps auxf  # lots of flag options, play with them
```


## Цель 2: Определить уровень использования серверного оборудования.

Определите степень загрузки оборудования (процессора, оперативной памяти, диска, сети) и выявите, есть ли проблемы с какими-либо из этих ресурсов.

Мы можем использовать  [[top]] (или более удобную программу [[htop]], если она установлена) для определения текущей загрузки памяти и процессора .

Тут у нас 2 варината:
1. У нас закончился какой-то ресурс, и надо понять какой
2. Ресурсы свободны, но сервер все равно работает медленно и это значит, что он ждет какой-то внешний сервис.

### Ветка 1: Кончились ресурсы

#### Проверка процессора
Посмотрим вывод команды [[top]]/[[htop]]. Посмотрим колнку procs в [[vmstat]] что бы понять сколько задач ожидают своей доли.
``` bash
vmstat 2 3 # 3 раза с интервалом 2 секунды
```
Посмотрим загрузку по каждому логическому ядру. ([[mpstat]])
``` bash
mpstat -P ALL
```
#### Проверка памяти
Проверим память командой [[free]].
``` bash
free -h
```
Так же что в [[vmstat]], что в [[top]] мы могли увидеть нехватку оперативной памяти и использование [[swap]], в таком случае мы можем проверить не сделал ли ничего [[oom killer]]
``` bash
dmesg | grep -i oom
journalctl -k | grep -i oom
journalctl -k | grep -i "killed process"
```
#### Диск
Мы можем посмотреть статистику дисков через [[iostat]] и какие процессы используют диск в реальном времени через [[iotop]]. Проверить командой [[df]] свободное место и айноды. Можем проверить смарт отчет [[smartctl]]. 
``` bash
df -h # Своодное место
df -i # Айноды
iostat -xz 5 # Статистика диска
iotop -o # Использование диска в реальном времени 
smartctl -a /dev/sda1 # Смарт отчет
```

### Ветка 2: Ресурсы свободны

Нужно постучаться в свое приложение и если локально оно отвечает мгновенно, а снаружи тормозит, то нужно разбирать путь. Если у нас есть задержка:
- Ровная задержка, одинаковая для всех запросов означает что мы упираемся в кого-то одного и всегда ждем его фиксированное время. 
- Если большинство запросов быстрые, а каждый 10 висит несколько секунд, то нам нужно искать очередь, ведь это означает что ресурс кончается переодически под всплеск нагрузки. 
#### Сети
Просмотр портов через [[netstat]] и [[ss]]. Проверим сетевые интерфейсы, маршруты и проччие вещи командой [[linux/ip|ip]]. Доступность удаленных хостов командой [[ping]], путь пакетов командой [[traceroute]], [[mtr]] для просмотра этого в прямом эфире. [[dig]] для проверки [[DNS]]. [[curl]] для запросов к различным endpoints. Проверить порты с помощью [[nc]]. Посмотреть какие пакеты бегают через определенные сетевые интерфейсы [[tcpdump]]. 
``` bash
netstat -tuln # слушать TCP/UDP порты
ss -tulpn # порты + процессы
ip
ping google.com # проверить DNS и доступность
traceroute google.com # Построить маршрут до узла
dig google.com # Получить A-запись
curl https://example.com # Выполнить GET-запрос
nc -zv 127.0.0.1 22               # проверить открыт ли порт
sudo tcpdump # Захватывать пакеты на основном интерфейсе
```


#### База данных
У баз данных в основном могут ломаться 4 вещи:
1. Кончились подключения. 
	Тут можно совершиь банальную ошибку - увидев исчерпанный пул, первым делом хочется его увеличить. Иногда это действительно может помочь, но часто может сделать ситуацию еще хуже, ведь каждое подключение к базе данных стоит ей памяти и процессорного времени, а число запросов которые она реально готова тянуть ограничеснно ее ядрами и дисками. Расширив пул мы не увеличим пропускную способность базы, а просто  перенесем очередь. До этого запросы ждали снаружи и все проходило +- бысьро, а теперь они ждут внутри базы медлеено мешая друг другу. 
2. Медленные запросы.
	Можно обнаружить запрос который идет очень долго, потому что данных стало больше чем в тот момент когда этот запрос придумали, а нужный индекс так и не сделали. 
3. Блокировки.
	Один запрос держит строку или таблицу и остальные ждут пока этот запрос отпустит ее
4. Рабочие данные перестали помещаться в память.
	Как только рабочие данные перестают помещаться в памяти, каждый запрос начинает ходить на диск.
