Главная идея траблшутинга — **не запускать команды наугад**, а постепенно сужать область поиска проблемы.

Примерный порядок:
```
Что делает сервер?
        ↓
Что именно работает неправильно?
        ↓
Есть ли нехватка ресурсов?
       / \
     да   нет
     ↓     ↓
CPU/RAM/   приложение /
Disk/Net   сеть / БД /
           внешний сервис
```

---

## 1. Понять, что делает сервер

Сначала нужно определить назначение сервера и какие сервисы на нём работают.Посмотреть слушающие порты и процессы:
``` bash
sudo ss -tulpn
```

`netstat` тоже может использоваться, но считается устаревающим:
``` bash
sudo netstat -tulpn
```

Посмотреть процессы:
``` bash
ps auxf
```

Если сервис работает через [[systemd]], посмотреть его состояние:
``` bash
systemctl status nginx
systemctl status <service>
```

Посмотреть последние ошибки:
``` bash
journalctl -p err -b
journalctl -u <service>
```

Перед дальнейшей диагностикой желательно понять:
- что именно должен делать сервер;
- какой сервис работает неправильно;
- проблема постоянная или периодическая;
- проблема появилась после изменения или существовала раньше.

---

## 2. Проверить ресурсы

Сначала стоит понять, не закончился ли какой-нибудь системный ресурс:
- CPU;
- RAM;
- диск;
- I/O;
- сеть.

Общую картину удобно посмотреть через [[top]] или [[htop]]:
```
top
```

Дальше обычно возникает две ситуации:
1. **Какой-то ресурс перегружен** → ищем причину перегрузки.
2. **Ресурсы свободны, но сервис тормозит** → ищем ожидание: сеть, БД, DNS, внешний API, блокировки и т. д.

---

## CPU

Смотрим загрузку CPU через [[top]] или [[htop]].

Дополнительно:
```
vmstat 2 3
```

В блоке `procs` особенно интересны:
- `r` — процессы, ожидающие CPU;
- `b` — процессы, ожидающие I/O.

Если `r` постоянно значительно больше количества CPU-ядер, процессор может быть узким местом.

Загрузка каждого логического ядра:
``` bash
mpstat -P ALL 2
```

Также полезно посмотреть [[load average]].

---

## Память

Основная команда:
``` bash
free -h
```

Особенно смотрим на `available` а не просто на `free`, потому что Linux активно использует свободную RAM под кеш.

Дополнительно:
``` bash
vmstat 2
top
```

Если памяти действительно не хватало, мог сработать [[OOM killer]]:
``` bash
dmesg | grep -i oom
journalctl -k | grep -i oom
journalctl -k | grep -i "killed process"
```

Наличие данных в [[swap]] само по себе ещё не означает проблему. Важнее увидеть **активный swap in/out** и нехватку `available` RAM.

## Диск

### Свободное место
``` bash
df -h
```

### Свободные inode
``` bash
df -i
```

Можно столкнуться с ситуацией, когда место есть, но закончились inode и новые файлы создать невозможно.

### Нагрузка на диск

``` bash
iostat -xz 5
```
Подробнее: [[iostat]].

Посмотреть процессы, активно использующие диск:
``` bash
sudo iotop -o
```

### Состояние физического диска

``` bash
sudo smartctl -a /dev/sda
```
Подробнее: [[smartctl]].

---

## 3. Ресурсы свободны, но сервер тормозит

Если CPU, память и диски выглядят нормально, значит процесс часто **чего-то ждёт**.

Это может быть:
```
приложение
    ↓
DNS
    ↓
сеть
    ↓
reverse proxy
    ↓
база данных
    ↓
другой сервис/API
```

Полезно сначала обратиться к приложению **локально**.

Например:
``` bash
curl http://127.0.0.1:8080
```

Если локально ответ мгновенный, а через внешний адрес медленный - проблема, скорее всего, находится между клиентом и приложением.

Например:
``` bash
клиент → DNS → сеть → firewall → nginx → приложение
```

Если медленно уже через `localhost`, проблема находится внутри самого приложения или его зависимостей.

## Характер задержки

Поведение задержки тоже может дать подсказку.

### Все запросы тормозят примерно одинаково

Например:
```
2.0 s
2.1 s
2.0 s
2.1 s
```

Возможно, приложение постоянно ждёт один и тот же компонент:
- DNS;
- БД;
- внешний API;
- timeout;
- сетевое соединение.

### Большинство запросов быстрые, некоторые резко медленные

Например:
```
40 ms
35 ms
38 ms
4 s
42 ms
39 ms
5 s
```

Стоит искать:
- очередь;
- исчерпание connection pool;
- блокировки;
- периодические пики нагрузки;
- медленные запросы;
- garbage collection;
- фоновые задачи.

``` bash

```

Маршруты:
``` bash

```

Слушающие порты:
``` bash

```

DNS:
``` bash

```

Проверка доступности:
``` bash
ping 8.8.8.8

```

Если IP работает, а доменное имя нет — вероятна проблема с [[DNS]].

Маршрут до сервера: 
``` bash

```

``` bash

```

```

```

```

```

```

```


[[ip]] · [[ss]] · [[ping]] · [[traceroute]] · [[mtr]] · [[dig]] · [[curl]] · [[nc]] · [[tcpdump]]

# База данных

У проблем с БД часто встречаются несколько типичных причин.

## 1. Закончились подключения

У приложения может закончиться connection pool или сама БД может достичь максимального количества подключений.

При этом **увеличивать пул автоматически не стоит**.

Каждое подключение требует ресурсов БД. Если база уже работает на пределе, увеличение количества соединений может только ухудшить ситуацию:

```
маленький pool
    ↓
запросы ждут перед БД

огромный pool
    ↓
все запросы попадают в БД
    ↓
БД начинает выполнять их одновременно
    ↓
CPU / RAM / диск перегружаются
    ↓
все запросы становятся медленнее
```

Увеличение количества подключений не увеличивает автоматически производительность базы.

---

## 2. Медленные запросы

Запрос мог нормально работать раньше, но со временем данных стало намного больше.

Например:

```
SELECT * FROM users WHERE email = 'test@example.com';
```

Если нужного индекса нет, база может начать перебирать огромное количество строк.

Нужно искать:

- долгие запросы;
- отсутствие индексов;
- плохой query plan;
- большие table scan.

---

## 3. Блокировки

Одна транзакция может удерживать строку или таблицу:

```
Запрос A
   ↓
держит lock

Запрос B
Запрос C
Запрос D
   ↓
ждут
```

При этом CPU и память сервера могут выглядеть совершенно нормально.

---

## 4. Данные перестали помещаться в память

Пока активно используемые данные находятся в RAM, база может работать очень быстро.

Когда рабочий набор становится больше доступной памяти:

```
RAM
 ↓
закончился cache
 ↓
БД чаще читает данные с диска
 ↓
растёт latency
```

Особенно сильно это заметно при случайных чтениях с диска.

# Короткий алгоритм

Когда сервер работает неправильно:

```
1. Что делает сервер?
2. Что именно сломалось?
3. Когда это началось?
4. Что говорят логи?

5. CPU перегружен?
6. RAM закончилась?
7. Диск заполнен?
8. Диск перегружен?

Если нет:

9. Быстро ли приложение отвечает локально?
10. Работает ли DNS?
11. Работает ли сеть?
12. Доступен ли нужный порт?
13. Нормально ли работает БД?
14. Нет ли медленных запросов / locks / очередей?
15. Не ждёт ли приложение внешний сервис?
```

Именно этот последний блок я бы считал **ядром всей заметки**. Со временем, когда ты изучишь больше инструментов, ты сможешь просто добавлять их внутрь соответствующих веток, не превращая заметку в хаотичный справочник команд.

Примерный порядок:
``` text
Что делает сервер?
        ↓
Что именно работает неправильно?
        ↓
Есть ли нехватка ресурсов?
       / \
     да   нет
     ↓     ↓
CPU/RAM/   приложение /
Disk/Net   сеть / БД /
           внешний сервис
```


## Цель 1: Охарактеризовать сервер.

Выясните, чем занимается сервер; каково его назначение (например, веб-сервер, сервер баз данных, сервер обработки данных и т. д.).
``` bash
sudo netstat -tlpn  # becoming obsolete
sudo ss -tlpn  # more modern (same flags!)
```
Конечно, мы можем использовать этот метод [[ps]] и для перечисления всех процессов:
``` bash
sudo ps auxf  # lots of flag options, play with them
```


## Цель 2: Определить уровень использования серверного оборудования.

Определите степень загрузки оборудования (процессора, оперативной памяти, диска, сети) и выявите, есть ли проблемы с какими-либо из этих ресурсов.

Мы можем использовать  [[top]] (или более удобную программу [[htop]], если она установлена) для определения текущей загрузки памяти и процессора .

Тут у нас 2 варината:
1. У нас закончился какой-то ресурс, и надо понять какой
2. Ресурсы свободны, но сервер все равно работает медленно и это значит, что он ждет какой-то внешний сервис.

### Ветка 1: Кончились ресурсы

#### Проверка процессора
Посмотрим вывод команды [[top]]/[[htop]]. Посмотрим колнку procs в [[vmstat]] что бы понять сколько задач ожидают своей доли.
``` bash
vmstat 2 3 # 3 раза с интервалом 2 секунды
```
Посмотрим загрузку по каждому логическому ядру. ([[mpstat]])
``` bash
mpstat -P ALL
```
#### Проверка памяти
Проверим память командой [[free]].
``` bash
free -h
```
Так же что в [[vmstat]], что в [[top]] мы могли увидеть нехватку оперативной памяти и использование [[swap]], в таком случае мы можем проверить не сделал ли ничего [[oom killer]]
``` bash
dmesg | grep -i oom
journalctl -k | grep -i oom
journalctl -k | grep -i "killed process"
```
#### Диск
Мы можем посмотреть статистику дисков через [[iostat]] и какие процессы используют диск в реальном времени через [[iotop]]. Проверить командой [[df]] свободное место и айноды. Можем проверить смарт отчет [[smartctl]]. 
``` bash
df -h # Своодное место
df -i # Айноды
iostat -xz 5 # Статистика диска
iotop -o # Использование диска в реальном времени 
smartctl -a /dev/sda1 # Смарт отчет
```

### Ветка 2: Ресурсы свободны

Нужно постучаться в свое приложение и если локально оно отвечает мгновенно, а снаружи тормозит, то нужно разбирать путь. Если у нас есть задержка:
- Ровная задержка, одинаковая для всех запросов означает что мы упираемся в кого-то одного и всегда ждем его фиксированное время. 
- Если большинство запросов быстрые, а каждый 10 висит несколько секунд, то нам нужно искать очередь, ведь это означает что ресурс кончается переодически под всплеск нагрузки. 
#### Сети
Просмотр портов через [[netstat]] и [[ss]]. Проверим сетевые интерфейсы, маршруты и проччие вещи командой [[linux/ip|ip]]. Доступность удаленных хостов командой [[ping]], путь пакетов командой [[traceroute]], [[mtr]] для просмотра этого в прямом эфире. [[dig]] для проверки [[DNS]]. [[curl]] для запросов к различным endpoints. Проверить порты с помощью [[nc]]. Посмотреть какие пакеты бегают через определенные сетевые интерфейсы [[tcpdump]]. 
``` bash
netstat -tuln # слушать TCP/UDP порты
ss -tulpn # порты + процессы
ip
ping google.com # проверить DNS и доступность
traceroute google.com # Построить маршрут до узла
dig google.com # Получить A-запись
curl https://example.com # Выполнить GET-запрос
nc -zv 127.0.0.1 22               # проверить открыт ли порт
sudo tcpdump # Захватывать пакеты на основном интерфейсе
```

#### База данных
У баз данных в основном могут ломаться 4 вещи:
1. Кончились подключения. 
	Тут можно совершиь банальную ошибку - увидев исчерпанный пул, первым делом хочется его увеличить. Иногда это действительно может помочь, но часто может сделать ситуацию еще хуже, ведь каждое подключение к базе данных стоит ей памяти и процессорного времени, а число запросов которые она реально готова тянуть ограничеснно ее ядрами и дисками. Расширив пул мы не увеличим пропускную способность базы, а просто  перенесем очередь. До этого запросы ждали снаружи и все проходило +- бысьро, а теперь они ждут внутри базы медлеено мешая друг другу. 
2. Медленные запросы.
	Можно обнаружить запрос который идет очень долго, потому что данных стало больше чем в тот момент когда этот запрос придумали, а нужный индекс так и не сделали. 
3. Блокировки.
	Один запрос держит строку или таблицу и остальные ждут пока этот запрос отпустит ее
4. Рабочие данные перестали помещаться в память.
	Как только рабочие данные перестают помещаться в памяти, каждый запрос начинает ходить на диск.
